# 财务/合同审核Agent项目SKILLS

## 一、通用软件工程开发最佳实践（企业级应用基石）

### 1. 项目生命周期管理

- **采用迭代式增量开发**：将项目划分为 2-3 周的短迭代周期，每个迭代交付可运行的功能模块。先实现核心审核流程，再逐步添加高级功能（如多模态审核、智能风险预警）。
- **明确需求优先级**：使用 MoSCoW 方法（Must have/Should have/Could have/Won't have）区分需求优先级。财务 / 合同审核的核心功能（文本解析、规则匹配、结果输出）必须在第一个迭代完成。
- **建立清晰的变更管理流程**：所有需求变更必须经过书面申请和评估，避免随意修改导致的代码混乱和技术债务。

### 2. 代码质量与可维护性

- 遵循 SOLID 设计原则
  - 单一职责原则：每个类 / 函数只负责一件事。例如，将 PDF 解析、OCR 处理、规则引擎、结果生成等功能分离到独立模块。
  - 开闭原则：对扩展开放，对修改关闭。通过接口和抽象类实现新规则的添加，而不是修改现有代码。
  - 里氏替换原则：子类可以替换父类而不影响程序正确性。
  - 接口隔离原则：客户端不应该依赖它不需要的接口。
  - 依赖倒置原则：依赖抽象，不依赖具体实现。
- 代码规范与风格统一
  - 使用行业通用的代码风格指南（如 Python 的 PEP 8）。
  - 强制使用代码格式化工具（black、isort）和静态代码分析工具（flake8、mypy）。
  - 所有函数和类必须有清晰的文档字符串，说明功能、参数、返回值和异常。
- 模块化与组件化设计
  - 将系统拆分为高内聚、低耦合的独立模块。
  - 模块之间通过明确定义的接口进行通信，避免直接依赖内部实现。
  - 提取通用功能为可复用的工具类或库（如日志工具、配置管理、异常处理）。

### 3. 版本控制与协作

- 使用 Git 进行版本控制
  - 采用 Git Flow 或 GitHub Flow 工作流。
  - 主分支（main/master）始终保持可部署状态。
  - 所有开发工作在特性分支（feature branch）上进行，通过 Pull Request 合并到主分支。
- **强制代码审查**：所有代码变更必须经过至少一名其他开发者的审查才能合并。
- **提交信息规范**：使用统一的提交信息格式（如 Conventional Commits），便于生成变更日志和追溯历史。

### 4. 配置与依赖管理

- **外部化配置**：将所有配置信息（如 API 密钥、数据库连接、规则文件路径）从代码中分离出来，使用配置文件或环境变量管理。
- **依赖版本锁定**：使用 requirements.txt（Python）或 package-lock.json（Node.js）锁定所有依赖的精确版本，避免 "在我电脑上能运行" 的问题。
- **定期更新依赖**：建立定期更新依赖的流程，修复安全漏洞和 bug。

### 5. 错误处理与日志记录

- 全面的错误处理
  - 使用异常处理机制捕获和处理所有可能的错误，避免程序崩溃。
  - 定义自定义异常类，区分不同类型的错误（如解析错误、规则匹配错误、API 调用错误）。
  - 提供有意义的错误信息，帮助调试和问题定位。
- 结构化日志记录
  - 使用结构化日志格式（如 JSON），便于日志分析和监控。
  - 记录不同级别的日志（DEBUG、INFO、WARNING、ERROR、CRITICAL）。
  - 日志中必须包含时间戳、模块名、函数名和错误详情。

## 二、Agent 开发核心原则与最佳实践

### 1. Agent 架构设计原则

- 模块化 Agent 架构

  ：将 Agent 拆分为独立的核心组件，每个组件负责一个特定功能

  - **感知组件**：负责接收和解析输入（文本、PDF、图片等）。
  - **记忆组件**：存储对话历史、审核上下文和中间结果。
  - **推理组件**：执行逻辑推理、规则匹配和决策。
  - **工具调用组件**：调用外部工具（如数据库、搜索引擎、OCR 服务）。
  - **行动组件**：执行具体操作（如生成报告、发送通知、更新数据库）。

- **清晰的状态管理**：明确 Agent 的状态转换流程，避免状态混乱和不可预测的行为。

- **可解释性优先**：Agent 的每一个决策都必须能够被人类理解和解释，这对于财务 / 合同审核这类高风险应用至关重要。

### 2. LLM 使用最佳实践

- 提示工程最佳实践
  - 使用结构化提示词（如 XML 标签、JSON 格式）明确指令和输出格式。
  - 提供清晰的角色定义和任务描述。
  - 使用少样本学习（Few-shot learning）提高输出质量。
  - 加入思维链（Chain of Thought）引导，让 LLM 逐步推理。
- **提示词版本控制**：将所有提示词存储在单独的文件中，并纳入版本控制，便于跟踪和回滚。
- **LLM 调用封装**：将 LLM 调用封装为独立的服务或类，统一处理错误重试、超时、限流和日志记录。
- **输出验证与解析**：始终验证 LLM 的输出格式和内容，避免无效或错误的输出导致程序崩溃。

### 3. 工具调用与集成

- **工具抽象层**：定义统一的工具接口，所有工具都实现相同的接口，便于添加新工具和替换现有工具。
- 工具调用安全
  - 限制工具的权限，遵循最小权限原则。
  - 对工具调用的参数进行严格验证。
  - 记录所有工具调用的详细信息，便于审计和调试。
- **异步工具调用**：对于耗时较长的工具调用（如 OCR 处理、数据库查询），使用异步方式执行，提高 Agent 的响应速度。

### 4. 记忆管理

- 分层记忆架构
  - **短期记忆**：存储当前对话和审核任务的上下文。
  - **长期记忆**：存储历史审核记录、规则库和知识库。
- **向量数据库用于语义检索**：使用向量数据库（如 Chroma、Pinecone）存储和检索非结构化数据（如合同文本、财务报表）。
- **记忆修剪与总结**：定期对长期记忆进行修剪和总结，避免记忆过载和检索效率下降。

## 三、财务 / 合同审核类 Agent 特定开发经验

### 1. 数据处理与解析

- **多格式支持**：支持常见的财务 / 合同文件格式（PDF、Word、Excel、图片）。
- 专业 OCR 与解析
  - 使用专业的 OCR 服务（如阿里云 OCR、腾讯云 OCR）处理扫描件和图片。
  - 针对财务报表和合同文本优化解析规则，准确提取表格、条款和关键信息。
- **数据标准化**：将提取的信息转换为统一的结构化格式（如 JSON），便于后续处理和分析。

### 2. 规则引擎设计

- **规则与代码分离**：将审核规则存储在独立的配置文件或数据库中，而不是硬编码在代码里。
- 支持多种规则类型
  - **硬规则**：明确的、不可违反的规则（如合同金额必须大于 0、发票号码格式必须正确）。
  - **软规则**：需要人工判断的规则（如合同条款是否合理、财务数据是否异常）。
  - **组合规则**：由多个简单规则组合而成的复杂规则。
- **规则版本管理**：对规则进行版本控制，支持规则的回滚和历史查询。
- **规则执行日志**：记录每一条规则的执行结果和原因，便于审计和问题定位。

### 3. 风险评估与分级

- **建立风险分级体系**：将审核发现的问题分为不同的风险等级（如高、中、低）。
- **风险评分机制**：为每个风险点分配相应的分数，根据总分数确定整体风险等级。
- **风险预警**：对于高风险问题，自动触发预警机制，通知相关负责人。

### 4. 人机协作流程

- **明确人机分工**：Agent 负责处理重复性高、规则明确的审核任务，人类负责处理复杂、模糊和高风险的情况。
- **审核结果复核**：所有 Agent 的审核结果都必须经过人类复核才能生效。
- **反馈闭环**：建立人类反馈机制，将人类的审核意见反馈给 Agent，用于优化规则和模型。

## 四、技术栈选型建议（经过生产验证）

### 1. 核心技术栈

- **编程语言**：Python 3.10+（生态最丰富，适合 AI 和数据处理）
- **LLM 框架**：LangChain 0.2+（成熟稳定，社区活跃，支持多种 LLM 和工具）
- **向量数据库**：Chroma（轻量级，适合本地开发）或 Pinecone（云原生，适合生产环境）
- **Web 框架**：FastAPI（高性能，自动生成 API 文档）
- **数据库**：PostgreSQL（支持 JSON 和向量类型，适合存储结构化和半结构化数据）

### 2. 辅助工具

- **OCR 服务**：阿里云 OCR / 腾讯云 OCR（准确率高，支持多种格式）
- **PDF 处理**：PyPDF2、pdfplumber（文本提取）、pdf2image（PDF 转图片）
- **Excel 处理**：pandas、openpyxl
- **任务队列**：Celery（处理异步任务，如批量审核）
- **容器化**：Docker、Docker Compose（便于部署和环境一致性）

## 五、测试与质量保证策略

### 1. 单元测试

- 为所有核心函数和类编写单元测试，覆盖率至少达到 80%。
- 使用 pytest 作为测试框架。
- 使用 mock 对象模拟外部依赖（如 LLM 调用、数据库访问）。

### 2. 集成测试

- 测试模块之间的接口和交互。
- 测试完整的审核流程，从文件上传到结果输出。

### 3. LLM 输出测试

- 建立测试用例库，包含各种常见和边缘情况的财务 / 合同文件。
- 定期运行测试用例，评估 LLM 输出的准确性和一致性。
- 使用评估指标（如准确率、召回率、F1 分数）量化 LLM 的性能。

### 4. 安全测试

- 进行输入验证测试，防止 SQL 注入、XSS 等常见攻击。
- 测试权限控制机制，确保不同用户只能访问其权限范围内的数据。
- 进行数据泄露测试，确保敏感信息（如财务数据、商业秘密）得到妥善保护。

## 六、常见陷阱与避坑指南

1. **避免过度依赖 LLM**：不要让 LLM 处理所有逻辑，特别是规则明确的任务应该用传统代码实现。LLM 应该用于处理模糊、复杂和需要自然语言理解的部分。
2. **不要硬编码规则**：硬编码的规则难以维护和修改，应该使用独立的规则引擎。
3. **重视数据质量**：垃圾进，垃圾出。确保输入数据的准确性和完整性，否则审核结果将毫无意义。
4. **不要忽视可解释性**：在财务 / 合同审核领域，可解释性比准确率更重要。Agent 必须能够说明为什么做出某个决策。
5. **建立完善的日志和审计系统**：所有操作都必须有日志记录，便于审计和问题追溯。
6. **提前考虑性能问题**：随着审核任务量的增加，系统性能可能会下降。提前进行性能测试和优化，使用异步处理和任务队列提高系统吞吐量。
7. **不要跳过测试**：特别是对于高风险的财务 / 合同审核应用，充分的测试是必不可少的。

# 七、通用软件工程进阶实践（规避补丁式开发，保障可扩展性）

## 1\. 技术债务管理（核心避坑点）

财务/合同审核Agent作为企业级高风险应用，技术债务会直接导致后续维护成本激增、漏洞频发，需从开发初期建立债务管控机制，杜绝“先上线、后补丁”的粗放模式。

- **技术债务分类管控**：将债务分为“必须解决”（如规则引擎硬编码、无异常处理）、“可暂缓但需记录”（如日志格式不统一）两类，每个迭代预留20%时间用于偿还高优先级债务，避免债务堆积。

- **债务可视化与跟踪**：使用工具（如SonarQube）量化技术债务（代码重复率、未覆盖测试用例、违规代码），建立债务跟踪表，明确责任人、解决时限，纳入迭代考核。

- **禁止临时补丁**：所有临时解决方案（如紧急修复线上bug的临时代码）必须标注“临时”标签，且在下次迭代中彻底重构，严禁长期保留临时代码形成“牛皮癣”式实现。

## 2\. 可扩展性设计（适配业务迭代）

财务/合同审核规则、审核场景会随企业业务变化（如新增税种、合同类型）不断调整，需避免“改一处牵全身”，设计具备高扩展性的架构。

- **接口标准化与版本化**：所有内部模块接口、外部API均采用标准化设计，新增功能时采用接口版本迭代（如/v1/audit、/v2/audit），不修改原有接口逻辑，确保旧功能正常运行。

- **插件化架构设计**：将可扩展功能（如新增文件格式解析、自定义审核规则）设计为插件形式，通过配置文件动态加载，无需修改核心代码即可扩展功能。例如，新增“增值税发票审核”功能时，仅需开发对应插件并配置加载，不影响原有合同审核逻辑。

- **预留扩展接口**：在核心模块（如规则引擎、结果输出模块）预留扩展接口，例如支持自定义风险评分模型、自定义报告模板，适配未来业务升级需求。

## 3\. 环境一致性与部署规范

避免“本地能运行、测试通不过、线上出问题”的常见问题，建立全流程环境一致性机制，规范部署流程，减少环境差异导致的bug。

- **容器化标准化部署**：使用Docker\+Docker Compose封装开发、测试、生产环境，所有环境的依赖、配置完全一致，通过Dockerfile固化环境配置，禁止本地环境与部署环境存在差异。

- **部署流程自动化**：采用CI/CD流水线（如Jenkins、GitHub Actions）实现代码提交→静态检查→单元测试→集成测试→自动部署，全程自动化，减少人工操作失误，确保每一次部署的代码都是经过验证的稳定版本。

- **环境隔离与权限管控**：严格区分开发、测试、生产环境，开发环境仅用于功能开发，测试环境用于全量测试，生产环境仅部署经过验证的稳定版本；不同环境设置独立权限，禁止开发人员直接操作生产环境，避免误操作。

## 4\. 代码复用与组件沉淀

避免重复开发，减少冗余代码，沉淀可复用组件，提升开发效率的同时，降低维护成本。

- **通用组件沉淀**：将财务/合同审核中高频使用的功能（如文本提取、数据校验、日志记录、异常处理）封装为通用组件，纳入项目组件库，供所有模块复用，确保组件的统一性和可维护性。

- **公共工具类规范**：公共工具类（如日期处理、金额格式化、加密解密）需经过严格测试，明确功能边界，禁止在工具类中添加业务逻辑，确保工具类的通用性和无状态性。

- **代码复用审核**：在代码审查环节，重点检查是否存在重复开发的代码，鼓励开发人员复用现有组件和工具类，避免出现“重复造轮子”的情况。

# 八、Agent开发进阶实践（贴合审核场景，提升稳定性与可验证性）

## 1\. LLM调用优化（避免无效输出，提升可控性）

财务/合同审核对输出准确性要求极高，需优化LLM调用逻辑，避免LLM输出不可控、不规范的内容，杜绝因LLM输出错误导致的审核失误。

- **输出约束强化**：在提示词中明确输出格式（如JSON、固定模板），并添加“输出校验规则”，例如要求LLM输出的审核结果必须包含“审核项、结果、风险等级、依据”四个字段，缺失任何字段则视为无效输出，触发重试机制。

- **LLM分层调用策略**：根据任务复杂度分层调用LLM，简单任务（如文本提取、规则匹配）使用轻量型LLM（如Llama 3 8B），复杂任务（如模糊条款解读、异常数据判断）使用高性能LLM（如GPT\-4、文心一言4\.0），平衡效率与准确性；同时，对LLM输出进行多级校验，先由代码校验格式，再由规则引擎校验逻辑，最后由人工复核高风险结果。

- **缓存机制优化**：对高频重复的LLM调用（如相同类型合同的条款解读、固定财务规则的匹配）进行缓存，使用Redis存储缓存结果，设置合理的缓存过期时间，减少LLM调用次数，降低成本，同时提升响应速度；缓存内容需定期校验，确保与最新规则一致。

- **LLM降级策略**：当LLM服务异常（如超时、宕机）时，启用降级方案，例如调用备用LLM、使用预训练的规则模板生成基础审核结果，避免系统整体崩溃，保障审核业务连续性。

## 2\. 记忆管理进阶（提升审核连贯性，避免上下文丢失）

财务/合同审核往往需要结合上下文（如合同附件、历史审核记录、关联财务数据），需优化记忆管理，避免上下文丢失导致的审核偏差。

- **上下文切片与关联**：将审核任务的上下文（如合同主文本、附件、关联发票、历史审核意见）进行切片存储，通过唯一标识（如合同ID、审核任务ID）关联，确保Agent在审核过程中可随时调取相关上下文，避免因上下文过长导致的记忆过载。

- **记忆更新与同步**：当审核任务状态变更（如人工复核意见录入、规则更新）时，及时更新记忆组件中的相关内容，确保记忆与实际业务状态一致；同时，实现多Agent协作场景下的记忆同步（如财务审核Agent与合同审核Agent共享关联数据），避免数据不一致。

- **记忆校验与清理**：定期对记忆组件中的数据进行校验，删除无效、过期的记忆（如已完成审核且无需追溯的任务上下文），避免记忆冗余；同时，对敏感记忆数据（如财务报表、商业秘密）进行加密存储，确保数据安全。

## 3\. 规则引擎进阶（提升灵活性，降低维护成本）

财务/合同审核规则繁多且易变更，需进一步优化规则引擎，实现规则的灵活配置、快速迭代，避免规则维护依赖开发人员。

- **可视化规则配置**：开发可视化规则配置界面，允许业务人员（如财务审核员、法务）直接配置审核规则，无需编写代码。例如，通过拖拽组件配置“合同金额\&gt;100万需总经理审批”“发票日期晚于合同日期视为异常”等规则，配置完成后自动同步到规则引擎，即时生效。

- **规则冲突检测**：规则引擎添加冲突检测机制，当新增或修改规则时，自动检测该规则与现有规则是否存在冲突（如“合同金额\&gt;100万需审批”与“合同金额\&gt;200万需审批”无冲突，“合同金额\&gt;100万需审批”与“合同金额\&gt;100万无需审批”存在冲突），并提示用户修改，避免规则冲突导致的审核错误。

- **规则灰度发布**：新增或修改的规则采用灰度发布策略，先在小范围审核任务中试用，收集反馈并优化，确认无问题后再全面推广，避免新规则直接上线导致的批量审核失误。

- **规则追溯与回滚**：对每一次规则变更进行记录，包括变更人、变更时间、变更内容，支持规则版本回滚，当新规则出现问题时，可快速回滚到上一个稳定版本，降低故障影响。

## 4\. 人机协作进阶（提升效率，降低风险）

财务/合同审核不能完全依赖Agent，需优化人机协作流程，明确分工，实现“Agent提效、人工把关”，降低审核风险。

- **智能任务分配**：根据审核任务的风险等级、复杂度，自动分配给Agent或人类审核员。低风险、规则明确的任务（如常规发票审核、标准合同条款审核）由Agent处理；高风险、复杂模糊的任务（如异常财务数据审核、非标准合同条款解读）自动分配给人类审核员，同时提供Agent生成的初步审核意见，辅助人类决策。

- **反馈驱动优化**：建立完善的人类反馈收集机制，人类审核员对Agent的审核结果进行修正时，需填写修正原因（如“规则匹配错误”“LLM解读偏差”），系统自动将反馈信息关联到对应模块，用于优化规则引擎、提示词和LLM模型，形成“审核\-反馈\-优化”的闭环。

- **审核痕迹全程可追溯**：记录审核全流程痕迹，包括Agent的每一步操作、LLM的输出结果、人类审核员的修正意见、规则的执行过程，形成完整的审核日志，便于审计、问题追溯和责任认定。

# 九、财务/合同审核Agent专项实践（针对性避坑，保障合规性）

## 1\. 敏感数据安全（核心合规要求）

财务数据、合同信息属于企业敏感信息，需严格保障数据安全，避免数据泄露、篡改，符合《数据安全法》《个人信息保护法》等合规要求。

- **数据加密存储与传输**：所有敏感数据（如财务报表、合同文本、客户信息）在存储时采用AES加密，传输时采用HTTPS协议，确保数据在存储和传输过程中不被泄露、篡改。

- **数据访问权限精细化**：建立精细化的权限管控体系，根据用户角色（如财务审核员、法务、管理员）分配不同的数据访问权限，例如财务审核员仅能访问自己负责的财务审核任务，无法查看其他部门的合同信息；管理员拥有全部权限，但操作需留下审计痕迹。

- **敏感数据脱敏处理**：在非生产环境（如开发、测试环境）中，对敏感数据进行脱敏处理（如将身份证号、手机号、金额等信息替换为占位符），避免敏感数据泄露；生产环境中，仅在必要时展示完整敏感数据，且需进行访问权限校验。

- **数据留存与销毁**：根据企业合规要求，明确审核数据的留存期限，超过留存期限的 data 自动销毁，销毁过程全程记录，确保符合合规要求。

## 2\. 审核准确性保障（核心业务要求）

财务/合同审核的准确性直接关系到企业的资金安全、法律风险，需通过多重机制保障审核结果的准确性，避免因Agent失误导致企业损失。

- **多维度校验机制**：建立“规则校验\+LLM解读\+人工复核”的三重校验机制。规则引擎负责基础规则匹配，LLM负责复杂条款解读，人工负责高风险结果复核，确保审核结果无遗漏、无错误。

- **测试用例全覆盖**：建立完善的测试用例库，覆盖所有审核场景（如不同类型合同、不同税种发票、正常/异常数据），包括常规用例、边缘用例、异常用例（如虚假发票、无效合同），定期运行测试用例，评估Agent的审核准确性，及时发现并修复问题。

- **定期校准与优化**：每月对Agent的审核结果进行抽样检查，统计准确率、召回率等指标，分析错误原因（如规则不完善、LLM解读偏差、数据解析错误），针对性优化规则引擎、提示词和解析模块，持续提升审核准确性。

## 3\. 业务适配性优化（贴合企业实际需求）

不同企业的财务审核流程、合同类型、规则要求存在差异，需确保Agent具备业务适配性，避免“一刀切”的开发模式。

- **自定义配置能力**：允许企业根据自身业务需求，自定义审核流程、审核规则、风险等级、报告模板等，例如不同行业的企业可配置不同的财务审核规则（如制造业与服务业的发票审核规则差异），不同规模的企业可配置不同的风险分级标准。

- **多行业模板沉淀**：沉淀不同行业（如制造业、服务业、互联网行业）的财务/合同审核模板，包括常用规则、报告模板、风险点，企业可直接复用并根据自身需求调整，降低部署和使用成本。

- **业务变更快速适配**：当企业业务发生变更（如新增业务线、调整审核流程）时，Agent能够通过简单的配置调整（如新增规则、修改流程）快速适配，无需大规模修改核心代码。

# 十、项目开发落地保障措施（杜绝无经验证代码，确保项目可控）

## 1\. 开发规范落地与监督

- 建立项目开发规范文档，明确代码风格、接口设计、模块划分、日志规范、测试要求等，所有开发人员必须严格遵循，避免无规范开发导致的代码混乱。

- 成立代码审查小组，每一次代码提交、Pull Request都必须经过审查，重点检查代码质量、合规性、可维护性，杜绝无经验证、存在漏洞的代码合并到主分支。

- 定期开展代码复盘，梳理开发过程中出现的问题（如代码冗余、规则硬编码、测试遗漏），总结经验教训，优化开发规范和流程。

## 2\. 测试体系完善与执行

- 建立“单元测试\+集成测试\+系统测试\+压力测试\+合规测试”的全流程测试体系，每个模块开发完成后必须先通过单元测试，再进行集成测试，系统开发完成后进行全面的系统测试和压力测试，确保系统稳定、高效运行。

- 专门成立测试小组，负责测试用例的设计、执行和维护，确保测试用例全覆盖，测试过程可追溯，测试结果真实有效；禁止开发人员自行测试自己开发的模块，避免测试不客观。

- 上线前进行全量回归测试，确保新增功能不影响原有功能，所有已知bug均已修复，避免上线后出现严重问题。

## 3\. 项目监控与问题应急

- 上线后建立完善的系统监控体系，监控系统性能（如响应时间、吞吐量）、Agent运行状态（如LLM调用成功率、规则执行成功率）、数据安全（如敏感数据访问记录），设置异常告警机制，当出现异常时及时通知相关负责人。

- 制定问题应急方案，针对常见问题（如LLM服务宕机、规则冲突、数据泄露）制定详细的应急处理流程，明确责任人、处理步骤和时间要求，确保问题出现后能够快速解决，降低影响。

- 定期开展应急演练，模拟各类异常场景，检验应急方案的有效性，优化应急处理流程，提升团队的应急处理能力。

# 十一、补充避坑指南

- 避免“过度设计”：无需为未来不确定的需求提前设计复杂架构，聚焦当前核心需求，采用“简单可用、逐步优化”的原则，避免过度设计导致的开发效率低下、代码冗余。

- 禁止“业务逻辑与技术实现耦合”：业务逻辑（如审核规则、流程）应与技术实现（如LLM调用、数据解析）分离，确保业务逻辑变更时，无需修改技术实现代码，降低维护成本。

- 不要忽视合规性开发：财务/合同审核涉及企业敏感数据和合规要求，开发过程中需提前考虑合规性，避免因合规问题导致项目返工或无法上线。

- 避免“重开发、轻维护”：项目开发完成后，需建立长期维护机制，定期更新依赖、修复bug、优化性能，避免系统上线后出现“无人维护”的情况，导致问题积累。
